Abstract. CivicVoice is an on-chain public petition and civic participation protocol built on BOT Chain. It enables individuals to publish petitions, collect wallet-based signatures, and receive official responses from registered organizations — all recorded transparently on the blockchain. This document describes the protocol architecture, identity limitations, privacy design, governance model, and security considerations.

1. Executive Summary

CivicVoice brings civic participation on-chain. Petitions are immutable records. Signatures are wallet transactions. Organization responses are permanent commitments. No central server can remove, censor, or alter any petition or signature once published.

Key properties:

  • Censorship-resistant. Petitions and signatures live on BOT Chain and cannot be deleted by any party after publication.
  • Transparent audit trail. Every signature, response, and status change is queryable on-chain.
  • Honest identity disclosure. CivicVoice does not claim signatures represent unique humans. One person may control many wallets.
  • Organization accountability. Registered organizations can post official responses and action updates, creating a verifiable public record of their commitments.

2. Protocol Architecture

2.1 Contract System

ContractRole
PetitionFactoryEntry point: creates petitions, enforces validation, owns pause control
PetitionRegistryStores all petition data, signature records, status, and indexes
SignatureManagerHandles wallet signing with duplicate prevention
OrganizationRegistryRegisters and verifies official organizations
ResponseRegistryStores org responses and creator updates per petition

2.2 Data Flow

Creator ──► PetitionFactory.createPetition() │ ▼ PetitionRegistry (stores petition, indexes by creator + category) Supporter ──► SignatureManager.sign(petitionId) │ ▼ PetitionRegistry.recordSignature() (checks: not signed, not expired, status Active) (updates: hasSigned[id][wallet] = true, currentSignatures++) (triggers: GoalReached if currentSignatures >= targetSignatures) Organization ──► ResponseRegistry.postResponse(petitionId, text, action) │ ▼ Stored on-chain, indexed by petitionId Creator ──► ResponseRegistry.postUpdate(petitionId, text) PetitionRegistry.closePetition(petitionId)

3. Petition Lifecycle

3.1 Creation

Any wallet can create a petition by calling PetitionFactory.createPetition() with:

  • Title (1–200 characters)
  • Description (1–5,000 characters)
  • Category (up to 60 characters)
  • Target signature count (> 0)
  • Deadline (Unix timestamp, or 0 for no deadline)

All text is stored directly on-chain. There is no IPFS, no centralized storage, no backend.

3.2 Signing

Any wallet can sign any Active petition by calling SignatureManager.sign(petitionId). The contract enforces:

  • Petition must be in Active status
  • Deadline must not have passed (if set)
  • The signing wallet must not have already signed this petition

3.3 Status Transitions

Active ──► GoalReached (auto: when currentSignatures >= targetSignatures) Active ──► Closed (by creator or admin) Active ──► Cancelled (by creator, only if 0 signatures) GoalReached ──► Closed (by creator or admin)

There is no "reactivation" — status transitions are one-directional.

4. Identity Model & Limitations

⚠️ Important Disclosure CivicVoice records wallet signatures, not unique human identities. One person may control multiple wallets and sign the same petition multiple times using different addresses. CivicVoice makes no claim that signature counts represent unique individuals.

This is a fundamental constraint of pseudonymous blockchain technology. Meaningful interpretation of petition signatures requires acknowledgment of this limitation by petition creators, recipients, and observers.

Potential mitigations (not implemented in v1.0):

  • Integration with on-chain identity or proof-of-humanity protocols
  • Social verification via organization-issued credentials
  • Sybil-resistance mechanisms such as token holding requirements or staking

These mitigations are considered for future versions. The v1.0 protocol is intentionally transparent about its limitations rather than making false claims of uniqueness.

5. Organization Participation

Organizations register once via OrganizationRegistry.registerOrganization() with their name, type, and website. The platform admin can mark organizations as verified, adding a visual badge but not granting extra on-chain permissions.

Registered organizations can:

  • Post official responses to any petition via ResponseRegistry.postResponse()
  • Include a free-text action field describing steps taken

All responses are permanent and publicly readable. Organizations cannot delete or modify posted responses.

6. Privacy Considerations

All data stored on BOT Chain is public and permanently visible to anyone with chain access. This applies to:

  • Petition text (title, description)
  • Signing wallet addresses
  • Organization responses
  • Creator updates
ℹ️ Privacy Warning Users must not publish personally identifiable information, private data, confidential communications, or anything they would not want permanently and publicly associated with their wallet address.

CivicVoice does not and cannot support private or confidential petitions in v1.0. Any sensitive petition content should be handled through off-chain channels with only a reference hash stored on-chain — this feature is not implemented in the current version.

7. Governance & Moderation

CivicVoice is a permissionless publishing protocol. The platform owner controls:

  • Emergency pause on petition creation and signing
  • Organization verification badges

The platform owner cannot: delete petitions, remove signatures, alter petition text, or prevent organizations from responding. These immutability properties are enforced by the smart contracts.

Moderation in v1.0 is limited to pausing new submissions during emergencies. Petition content is the responsibility of the creator. Illegal content published on-chain remains visible at the smart contract level regardless of frontend access.

9. Deployment Summary

See deploy.md for the full guide. Deploy order:

  1. PetitionRegistry — no constructor args
  2. OrganizationRegistry — no constructor args
  3. PetitionFactory — takes PetitionRegistry address
  4. Call registry.setFactory(factoryAddress)
  5. SignatureManager — takes PetitionRegistry address
  6. Call registry.setFactory(signatureManagerAddress)
  7. ResponseRegistry — takes OrgRegistry + PetitionRegistry addresses

Update the CONFIG block in index.html and set DEMO = false.
